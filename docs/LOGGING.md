# 模型诊断日志

## 设计

记录机器人自主调用及后端实际提供的动态上下文，帮助排查为何回复、为何沉默、调用了哪些工具以及发送是否成功。功能默认开启，可通过配置关闭，不改变模型决策、权限或工具执行行为。

同一次处理通过独立链路编号关联，嵌套阶段有独立编号及父编号；并发处理互不混淆。群聊参与判断与随后回复属于同一链路，独立后台审核和认知提取拥有自己的链路。

动态消息、个人及群认知、工具参数与结果、模型可见输出保留内容。系统固定提示词及本地人设、风格文件以标识、字符数和内容摘要替代；图片只保留类型和上下文位置，省略内嵌图片数据。凭据、授权头和内部推理不记录。日志是本机诊断数据，不用作机器人长期记忆，也不向 QQ 发送。

## 开发

`plugins/assistant/trace.py` 使用 `ContextVar` 关联异步调用，以 `trace_id`、`span_id`、`parent_span_id` 标识链路与阶段。`scoped` 装饰器记录阶段起止、耗时、取消和异常类型，`emit` 生成独立 JSONL 事件。`Config.model_trace_enabled` 控制记录，`model_trace_retention_days` 控制保留天数。

- `llm.py` 在模型请求前记录实际消息、条数、各条序列化长度、开放工具及输出上限；请求后记录正文与工具调用。两条工具执行路径记录参数、结果、状态及耗时。
- `dsh.py` 的 `dsh_view_sync` 记录浏览队列每次补写的成功数量、占用会话数量、异常类型和下次检查间隔，不包含会话正文或原生异常正文。普通业务日志仅在占用、恢复或错误类型变化时提示，持续同类状态不会刷屏。
- `http.py` 记录 HTTP 状态、耗时、Token 用量和服务商结束原因，不记录请求头或原始响应体。
- `groupchat.py` 记录触发消息标识、话题判断结果、固定参与门槛及跳过或过时取消原因。`topic_assignment_invalid`、`topic_assignment_repaired`、`topic_assignment_fallback` 分别记录单条校验失败、重判通过和保守留存，包含平台消息编号及固定 `error_code`；失败事件还包含尝试次数。`topic_assessment_failed.error_code` 区分整批请求失败与单条重判请求失败，不记录原始异常正文。
- `service.py` 记录业务请求编号、去重和限流、最终文本或表情发送结果、输出分段和截断情况。
- `memory.py`、`longterm.py` 记录会话裁剪、持久历史保留条数、认知与相关历史选取数量和摘录长度上限。日志反映实际取用范围，不读取全部历史来统计未选中总数。

固定提示词在日志副本中折叠，不修改发给模型的对象。配置中的密钥及结构化敏感字段被过滤；未知密钥若作为无标识的普通聊天文字出现，无法保证自动识别。图片 Base64 省略，远程图片地址保留并过滤可识别的敏感参数。内部推理及加密推理内容省略。

文件按北京时间日期命名，单文件达到 10 MB 后在下次写入前归档；单个事件可超过轮转阈值，不截断动态上下文。每次写入时清理超过保留天数的诊断文件。使用进程内锁串行写入，日志写入异常仅报告异常类型，不中断聊天。业务日志仍保持原有概要格式。

## 使用说明

`.env` 可配置以下选项，修改后重启机器人：

```dotenv
MODEL_TRACE_ENABLED=true
MODEL_TRACE_RETENTION_DAYS=7
```

省略配置时默认开启，保留 7 天。设为 `false` 停止产生新的模型诊断记录，原有诊断文件及普通业务日志不会被删除；关闭期间不执行诊断文件清理。

日志位于 `logs/model/trace-YYYY-MM-DD.jsonl`，每行一个 JSON 对象。该目录已被 Git 忽略。文件包含动态聊天原文与认知，仅供本机维护者查看。

排查步骤：

1. 找到 `request_received` 或 `group_trigger` 中对应的机器人、会话和消息编号，再按 `trace_id` 筛选整条链路。
2. 查看 `topic_decision`、`topic_assessment_failed`，确定是否参与及跳过原因；单条编号或归属校验失败时，按消息编号关联 `topic_assignment_invalid` 与随后的 `topic_assignment_repaired` 或 `topic_assignment_fallback`，错误类别说明见[话题模块](TOPICS.md)。
3. 查看 `model_context` 了解实际输入，固定提示词可按标识到默认目录或后台配置核对；摘要用于判断版本是否一致，不保存旧版本全文。
4. 按 `span_id` 查看 `model_output`、`http_usage` 和 `http_end`；工具执行通过 `call_id` 对应 `tool_start`、`tool_end`。模型请求工具不代表执行成功。
5. 查看 `send_result`、`send_skipped` 和错误事件。`stage_end` 的完成只代表该阶段函数返回，业务结果以发送、跳过及错误事件为准。

验证时发送一次需要查询的消息，检查上下文、工具执行和发送事件；再关闭开关、重启并发送消息，确认诊断文件不再增长。若没有生成日志，先确认开关与机器人运行状态，再检查业务日志中的 `model_trace_write_failure` 及目录写入权限。

群话题日志独立保存于 `logs/topics.sqlite3`，始终记录，不受模型诊断开关控制，沿用相同的凭据过滤和保留天数。后台“话题日志”仅展示有成功回复的话题，完整聊天不按模型输入窗口截取，规则与验证见[话题模块](TOPICS.md)。
