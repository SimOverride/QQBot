# 定时消息插件

## 设计

群管理员通过自然语言提出固定文字的发送时间，模型整理为待确认提议；原发起人在同群确认后才创建任务。支持北京时间的单次发送和每天定时发送。时间或正文不明确时应追问，模型不能自行补造内容。当前不支持每周、自定义间隔、到时调用模型生成内容、图片或真正的群@操作。

查看、创建和取消均限本群群管理员、群主或机器人主人。取消同样先提出建议，再由原发起人确认。确认码绑定账号、群和用户，五分钟有效且只能使用一次；新的提议覆盖该用户在本群的旧提议。确认时重新核验权限、开关、任务状态和首次执行时间。

每群最多20条活动任务，创建新任务时将结束记录缩减到最近80条。消息正文为1至1000字的固定文字，作为文字段发送，其中的CQ码不会被解释为平台操作。

离线、进程停止、插件停用期间错过的执行不补发。恢复后每天任务继续下一次未来时刻，错过的单次任务结束。每次发生最多尝试发送一次，结果不明不重试；该规则优先避免重复消息，不能保证网络故障时必达。停用后保留任务数据，恢复时未来计划可继续，旧确认失效。已提交平台的发送不能撤回。

## 开发

`plugins/extensions/schedule.py` 提供 `manage_schedule` 工具，动作包括 `list`、`once`、`daily`、`cancel`。`at` 使用 `YYYY-MM-DD HH:MM` 或 `HH:MM`，按UTC+8解析；`text` 为固定正文，`job_id` 为取消目标。未用字段传null。

模型工具只读数据或写入内存中的待确认提议；`/定时 确认` 才将变更保存到 `data/plugins.json`。每条任务使用独立ID，保存类型、时间、正文、下次执行时间、任务状态、最近发送状态及创建者。用户不能通过工具参数指定其他群。

定时轮询每两秒检查一次，正常在线执行允许30秒处理延迟；晚于窗口、早于本次启动或连接、以及停用期间的发生全部跳过。重新开启记录生效时刻，避免快速关闭再开启时补发。每天任务直接推进到下一次未来时刻，不逐日补跑。

发送前原子保存占用状态，并将单次任务标为结束或推进每天任务的下次时间，然后调用平台发送。成功记为 `sent`，失败或超时记为 `unknown`；进程在发送期间中断可能保留 `attempting`，均不重试该次发生。每次发送前重新读取配置，使等待网络期间的取消和停用生效。成功取得平台消息ID时写入现有消息档案。

诊断事件包含 `schedule_proposed`、`schedule_confirmed`、`schedule_skipped`、`schedule_send`，使用任务ID及群、账号关联。迁移保留任务ID与进度，旧副本不重新激活已结束的任务。

## 使用说明

重启机器人加载插件后，在已绑定的群里@机器人，例如：

- “每天晚上八点发一句：记得签到。”
- “明天下午三点发消息：今晚活动改到九点。”
- “看看本群现在有哪些定时消息。”
- “取消编号为……的定时消息。”

机器人应返回准确的北京时间、文字内容及 `/定时 确认 确认码`。确认无误后，由同一人@机器人发送该指令。取消也要确认；需要修改任务时先取消旧任务，再提出新任务。

`/定时 待确认` 可查看后端保留的原始提议。若模型没有明确展示时间或正文，先用此指令核对，不要直接确认。每天时间已过则首次安排到明天；单次时间必须在未来，确认时首次时间已过会拒绝，需要重新提议。

停用本群使用 `/插件 本群 schedule 关闭`，恢复使用 `/插件 本群 schedule 开启`。全局关闭时须机器人主人先恢复全局开关。群积极性为0不影响已确认的定时任务；停止发送定时消息请关闭插件或取消任务。

排查顺序：检查是否在绑定群、是否以管理员身份@机器人、是否已完成确认、全局及本群开关是否开启、机器人是否在线，再查看任务最近状态及诊断日志。普通成员、其他群和私聊不能管理任务。重启不会丢失已确认任务，但未确认提议会丢失。

本机运行中可以切换开关，无须重启；代码升级需要重启。当前没有创建任何示例发送任务，验证真实发送需由群管理员自行提出并确认。
